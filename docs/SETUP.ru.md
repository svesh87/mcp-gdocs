# Настройка Google Workspace

Всё ниже делается один раз, в [Google Cloud Console](https://console.cloud.google.com/),
человеком с аккаунтом Google Workspace в той организации, внутри которой сервер будет
работать. Минут пятнадцать, и на последнем шаге нужен браузер.

В 2025 году Google переименовал OAuth consent screen в **Google Auth Platform**. Если
найденное где-то руководство говорит про «APIs & Services → OAuth consent screen» — оно
устарело; названия ниже актуальные.

## 1. Отдельный проект

**Menu → IAM & Admin → Create a Project**

| Поле | Что вписать |
|---|---|
| **Project name** | что угодно читаемое, например `mcp-gdocs`. Меняется потом |
| **Project ID** | генерируется из имени. **После создания не меняется** — жмите *Edit* сейчас, если это важно |
| **Location** | ваша **организация**, а не *No organization* |

Location — единственное поле, на котором стоит притормозить. Аудитория **Internal**, на
которой держится вся модель доступа из следующих шагов, доступна только проекту,
принадлежащему организации. Проект, созданный вне неё, сделать Internal потом нельзя —
только пересоздать.

Новый проект, а не существующий: OAuth-клиент и его консент-экран принадлежат проекту, а
в старом проекте всегда есть настройки, которые никто не помнит.

Биллинг не нужен: у этих четырёх API нет платного тарифа, который надо включать.

## 2. Включить четыре API

**Menu → APIs & Services → Library**, и для каждого из четырёх: найти, открыть, нажать
**Enable**.

| API | Идентификатор сервиса |
|---|---|
| Google Drive API | `drive.googleapis.com` |
| Google Sheets API | `sheets.googleapis.com` |
| Google Slides API | `slides.googleapis.com` |
| Google Docs API | `docs.googleapis.com` |

Поиск выдаёт соседей — ориентируйтесь на точное название и идентификатор. По запросу
Drive рядом лежат **Drive Labels API** (таксономии меток), **Google Drive Activity API**
(кто что открывал и правил) и **Google Drive MCP** (собственный MCP-эндпойнт Google для
Drive, к этому серверу отношения не имеет). Ни один из трёх не нужен: сервер ходит в Drive
API сам.

Или одной строкой, если есть CLI:

```bash
gcloud services enable drive.googleapis.com sheets.googleapis.com \
                       slides.googleapis.com docs.googleapis.com --project=<PROJECT_ID>
```

Невключённый API отвечает на каждый вызов 403-й, где названо само API и дана ссылка на
страницу, которая его включает, — по крайней мере это ошибка, которая говорит, что
делать.

## 3. Branding

**Menu → APIs & Services → OAuth consent screen** — оттуда открывается Google Auth
Platform. Отдельного пункта в меню консоли у него нет: раскройте стрелку у *APIs &
Services*. В проекте, где раздел ещё не открывали, первый заход — короткий мастер, в
котором этот шаг и следующий проходятся одной формой.

Проще открыть напрямую, чем искать в меню:

```
https://console.cloud.google.com/auth/branding?project=<PROJECT_ID>
https://console.cloud.google.com/auth/audience?project=<PROJECT_ID>
https://console.cloud.google.com/auth/clients?project=<PROJECT_ID>
```

**Google Auth Platform → Branding**

| Поле | Что вписать |
|---|---|
| **App name** | что человек увидит на консент-экране, например `mcp-gdocs` |
| **User support email** | ваш адрес или группа. Показывается на консент-экране |
| **App logo** | пропустить |
| **App domain**, **Authorised domains** | пропустить — это нужно External-приложениям, проходящим верификацию |
| **Contact information → Email address** | куда Google пишет про проект. Ваш адрес |

Дальше — галочка **I agree to the Google API Services: User Data Policy** и завершение.

## 4. Аудитория: Internal

**Google Auth Platform → Audience → User type: Internal**
([прямая ссылка](https://console.cloud.google.com/auth/audience))

Это решение, из-за которого всё остальное простое. При Internal:

- консент могут пройти только аккаунты вашей организации — утёкший идентификатор клиента
  не даёт входа никому снаружи;
- нет верификации, хотя `drive` — restricted-скоуп. Для External-приложения тот же скоуп
  означает ревью Google и security assessment;
- нет экрана-предупреждения «unverified app» и нет потолка в 100 пользователей.

**External** — запасной вариант, если аккаунт личный `@gmail.com`, а не Workspace. Он
работает, с двумя отличиями: каждый входящий аккаунт придётся добавить в **Audience →
Test users**, а на консент-экране будет предупреждение о непроверенном приложении. Для
сервера, который человек поднимает себе, это терпимо.

## 5. OAuth-клиент типа Desktop

**Google Auth Platform → Clients → Create client**
([прямая ссылка](https://console.cloud.google.com/auth/clients))

| Поле | Значение |
|---|---|
| **Application type** | **Desktop app** |
| **Name** | любое, например `mcp-gdocs desktop`. Видно только в консоли |

Дальше **Create** и **Download JSON** на появившемся клиенте.

Desktop — не косметический выбор. Клиенту этого типа Google разрешает редирект на любой
loopback-адрес **без регистрации его в консоли**, и именно поэтому оба пути входа
работают без единой дополнительной настройки: и временный порт команды `login`, и
опубликованный порт контейнера на `127.0.0.1`. Клиент типа **Web application** потребовал
бы заранее перечислить каждый адрес редиректа, и вход ниже упал бы с
`redirect_uri_mismatch`.

Скачанный файл называется `client_secret_<длинный id>.apps.googleusercontent.com.json`.
Переименуйте его в `gcp-oauth.keys.json` и положите туда, откуда его будет читать сервер.
Внутри:

```json
{"installed": {
  "client_id": "…apps.googleusercontent.com",
  "client_secret": "…",
  "auth_uri": "https://accounts.google.com/o/oauth2/auth",
  "token_uri": "https://oauth2.googleapis.com/token"
}}
```

Сервер читает `installed` (и принимает `web` — чтобы неверный тип клиента упал внятным
сообщением при входе, а не ошибкой разбора). `auth_uri` и `token_uri` необязательны: по
умолчанию берутся гугловые.

**А можно вообще без файла.** Значимого в нём ровно две вещи — идентификатор и секрет, — и
их можно отдать переменными окружения:

```bash
GOOGLE_OAUTH_CLIENT_ID=…apps.googleusercontent.com
GOOGLE_OAUTH_CLIENT_SECRET=…
```

Это та форма, в которой их отдаёт хранилище паролей, и на диске о приложении не остаётся
ничего. Выньте два значения из скачанного файла, положите туда, где живут секреты, а файл
удалите. Если есть и файл, и переменные, побеждают переменные.

## 6. Скоупы

**Google Auth Platform → Data Access**
([прямая ссылка](https://console.cloud.google.com/auth/scopes)) — и для Internal-приложения
делать на этой странице нечего. Скоупы запрашивает сам сервер при входе, а для Internal они
и не показываются на консент-экране, и не проходят ревью. Страница нужна
External-приложениям, где заявленный список обязан совпадать с тем, что просит приложение:
**Add or remove scopes** выбирает из скоупов тех API, что включены на шаге 2 — только они и
перечислены, — а *Manually add scopes* принимает то, чего в списке нет.

Четыре, которые сервер запрашивает по умолчанию:

```
https://www.googleapis.com/auth/drive
https://www.googleapis.com/auth/spreadsheets
https://www.googleapis.com/auth/presentations
https://www.googleapis.com/auth/documents
```

Полный `drive`, а не узкий `drive.file`, — сознательно: `drive.file` видит только файлы,
созданные самим приложением, и потому не может открыть шаблон, с которого копируется
колода. Флаг `--scopes` сужает список без пересборки, по алиасу или полному URL:

```bash
mcp-gdocs --scopes presentations,drive.readonly …
```

Смена скоупов означает повторный вход: токен несёт те скоупы, с которыми он выдан.

## 7. Первый вход

На машине с браузером:

```bash
mcp-gdocs login --credentials ./gcp-oauth.keys.json --token-dir ./tokens
```

Команда печатает адрес, ждёт на loopback-порту и пишет `tokens/token.json`, когда браузер
вернётся. Входить надо тем аккаунтом, от чьего имени должен работать сервер.

Если сервер в контейнере, браузера внутри нет — вход идёт через собственную страницу
сервера. Поднимите его с `--transport=streamable-http`, опубликуйте порт на loopback и
откройте:

```
http://127.0.0.1:8819/login?key=<MCP_AUTH_TOKEN>
```

Страница показывает, входил ли кто-нибудь, какие права будут запрошены и где лежит файл
токена, и содержит одну кнопку. По нажатию браузер уходит на экран согласия Google, Google
возвращает его на `http://127.0.0.1:8819/oauth2callback` — ваш же опубликованный порт, —
так что код авторизации не покидает машину, и страница сообщает, что токен сохранён.

Детали, которые важны: ключ в адресе, потому что браузер не шлёт заголовок
`Authorization` сам по себе, — поэтому страница отдаётся с `Cache-Control: no-store` и
`Referrer-Policy: no-referrer`: ключ не должен уехать в Google рефером и осесть в кэше.
Переход к Google — отправка формы, а не ссылка, так что пересланный кому-то адрес
`/login` покажет ему страницу, а не затащит сразу на экран согласия. Обмен защищён PKCE
(`code_challenge_method=S256`), а сам вход просит offline-доступ с принудительным
консент-экраном: без этих двух вещей Google не отдаёт refresh-токен на повторном входе, и
сервер перестаёт работать в течение часа.

**Если сервер на другой машине**, не выставляйте этот порт наружу и не открывайте по
имени хоста: Google возвращает Desktop-клиент только на loopback-адрес, вход упал бы с
`redirect_uri_mismatch` — страница отказывает ещё раньше. Пробросьте порт, и адрес в
браузере снова станет loopback:

```bash
ssh -L 8819:127.0.0.1:8819 <хост>
# и открыть http://127.0.0.1:8819/login?key=… в локальном браузере
```

## 8. Где лежат два файла

Они разделены намеренно, и личный из них только один:

| Секрет | Что это | Где лежит |
|---|---|---|
| OAuth-клиент | приложение: кто именно просит консент | файл, путь к которому в `--credentials`, либо `GOOGLE_OAUTH_CLIENT_ID` и `GOOGLE_OAUTH_CLIENT_SECRET` в окружении. Раздаётся отдельно от образа тем, кому положено запускать сервер |
| `token.json` | консент одного человека, ставший refresh-токеном | пишется его собственным входом, 0600, в каталоге `--token-dir` |

Разделение идёт по тому, кто что пишет. Клиент читается один раз при старте и не меняется —
поэтому он спокойно приезжает из хранилища паролей двумя переменными и диска не касается.
Токен сервер перезаписывает при каждом обновлении access-токена — поэтому это файл, которым
владеет процесс: хранилище секретов не то место, куда программа пишет сама.

Ни тот, ни другой не коммитятся и не попадают в образ: оба в `.gitignore` и
`.dockerignore`, и сборка проверена — до контекста сборки не доезжает ни один.

## 9. Почему нет сервис-аккаунта

Сервис-аккаунт с domain-wide delegation убрал бы вход целиком — и именно поэтому его тут
нет.

Ключ такого аккаунта и есть весь доступ, а делегирование позволяет ему действовать от
имени любого сотрудника воркспейса, без его ведома и без следа в его собственных
настройках безопасности. Утечка образа или репозитория с таким ключом — компрометация
всех документов компании, а отзыв означает ротацию ключа, на котором держится половина
стека.

Личный токен достаёт ровно до того, до чего человек и так достаёт, виден в настройках его
собственного аккаунта и отзывается там в один клик.

## 10. Если что-то утекло

**Токен** — отозвать на
[myaccount.google.com/permissions](https://myaccount.google.com/permissions): найти
приложение, убрать доступ. Все выданные ему refresh-токены умирают сразу. Удалить
`token.json` и войти заново.

**Секрет клиента** — в консоли **Clients → нужный клиент → Reset secret**, потом раздать
новый `gcp-oauth.keys.json` тем, кто запускает сервер. Существующие токены работают до
ближайшего обновления, так что при серьёзной утечке их надо отозвать, как выше. При
аудитории Internal утёкший идентификатор клиента сам по себе входа не даёт: консент
всё равно требует аккаунта организации.

## 11. Ошибки, которые стоит узнавать в лицо

| Что написано | Что это значит |
|---|---|
| `no Google token yet` | никто не входил: `login` или `/login?key=…` |
| `invalid_grant` при обновлении | консент отозван или токен заменён. Войти заново |
| `redirect_uri_mismatch` | клиент не типа Desktop либо вход открыли не по loopback-адресу |
| `403` с названием API | это API не включено в проекте (шаг 2) |
| `403 PERMISSION_DENIED` на файле | вошедший человек до файла не достаёт — обычно это общий диск, куда его не добавили |
| `access_denied` на консент-экране | аудитория Internal, а аккаунт не из организации |
| `Google returned no refresh token` | повторный консент без принудительного экрана. Отозвать доступ приложения и войти заново |
